## 2. Prebook call sites and lifecycle trace

`prebookFlight` has exactly **one** call site in production code:

- `backend/src/modules/bookings/adapters/nuitee-flight-booking.provider.ts` →
  `prebookOnce()` → `NuiteeFlightService.prebookFlight()` → `POST /flights/prebooks`.

Everything else reaches it through `BookingsService`:

| # | Stage | Entry point | Provider call | Hold |
|---|---|---|---|---|
| 1 | Search / select | Flutter search | `POST /flights/rates` | No |
| 2 | Prepare | `POST /bookings/prepare` | `revalidateBooking(offerId)` | **was: 1** → now: `POST /flights/verify` (no hold) |
| 3 | Review | `POST /bookings/revalidate` | `revalidateBooking(offerId, { offerSnapshot })` | `GET /flights/prebooks/{id}` (if a legacy prebook exists) + `POST /flights/verify` — **0** |
| 4 | Offer check | `POST /offers/revalidate` | `verifyFlightOffer` | **0** |
| 5 | Confirm | `POST /bookings` | `revalidateBooking(offerId, { travelers, offerSnapshot })` | `POST /flights/prebooks` with the REAL party — **1** |
| 6 | Confirm retry (same party) | `POST /bookings` | same | `GET /flights/prebooks/{id}` — **0** |
| 7 | Booking | `createBooking` | `POST /flights/bookings` | consumes the prebook — **0** |
| 8 | Failure / abandon | — | — | the confirm-time prebook is retained |

Fields recorded per stage: prebook id, party, price, currency, expiration
(`servicesAttachable.expiresAt` for a prebook, `journey.expiration` for a
verify), snapshot fields (`offerId`, `prebookId`, `transactionId`,
`travelerFingerprint`), idempotency, and hold disposition.

## 3. Exact LiteAPI contract evidence

Source: the authoritative Flights OpenAPI specification
(`https://docs.liteapi.travel/openapi/openapiflights.json`, 311 KB, fetched
2026-11-08) plus the linked guides.

### 3.1 Complete flight endpoint inventory (OpenAPI `paths`)

```
POST /flights/rates
POST /flights/rates/matrix
POST /flights/verify
GET  /flights/prebooks/{prebookId}
POST /flights/prebooks/{prebookId}/services
POST /flights/prebooks
POST /flights/bookings
GET  /flights/bookings
GET  /flights/bookings/{bookingId}
GET  /flights/bookings/{bookingId}/services
POST /flights/bookings/{bookingId}/services
POST /flights/bookings/{bookingId}/services/confirm
GET  /flights/bookings/{bookingId}/cancellations
POST /flights/bookings/{bookingId}/cancellations
POST /flights/bookings/{bookingId}/extra-charges/precharges
POST /flights/bookings/{bookingId}/extra-charges/charges
PUT  /flights/bookings/{bookingId}/extra-charges/charges
GET/POST /data/flights/*
```

**There is no `DELETE`/`PUT`/`POST` for `/flights/prebooks/{prebookId}` other
than `/services`.** Cancellation exists only for confirmed **bookings**.

### 3.2 Cited contract statements

| Claim | Exact contract location |
|---|---|
| A prebook **reserves inventory** | `POST /flights/prebooks` description: "Initiate a flight booking session by **reserving the offer with the provider**, creating a payment intent when you use the Stripe SDK, and discovering available ancillary services" |
| The documented flow is **verify then one prebook** | `docs/booking-flow-recipes`: "Search → Verify → Prebook → Book"; `docs/build-a-flight-booking-experience`: "You cannot book without a prebook. You cannot prebook without a verified offer." |
| Verify is the **binding price** step | `POST /flights/verify`: "Confirm a flight offer is still available and retrieve the latest pricing before proceeding to booking"; recipe: "Confirm the offer is still live and get a binding price." |
| Prebook passengers **cannot be updated** | The only mutating prebook operation is `POST /flights/prebooks/{prebookId}/services`: "Set the **ancillary selection (seats / bags)** on an existing prebook" — "Each call **replaces** the prebook's current selection". No passenger field is accepted. |
| No prebook **release/cancel** | `FlightBooking.cancelIntentAt` description: "Not applicable to prebook endpoints." The only cancellation paths are `/flights/bookings/{bookingId}/cancellations`. |
| No documented prebook **expiry/auto-release** | The only expiration fields in the whole spec are `FlightOffer.expiration` ("Offer expiration time") and `servicesAttachable.expiresAt` ("Expiry time for attaching services"). `docs/flight-booking-architecture` §Session Expiry says only: "Sessions expire when the `offerId` or `prebookId` can no longer be used. Enforce expiry server-side." |
| Booking from a prebook is **idempotent** | `POST /flights/bookings`: "**Idempotent**: Returns the existing booking (HTTP 200 + `data[0].message`) if one already exists for the given `prebookId`. … Concurrent duplicate requests while a book is in progress return HTTP 409 (`45035`)." |
| Prebook retrieval is **read-only** | `GET /flights/prebooks/{prebookId}`: "Retrieve an existing flight checkout session (prebook) by ID"; "Reuse payment intent — Returns the stored Stripe `transactionId` / `secretKey` as-is (GET does not create or refresh a PaymentIntent)". |

## 4. Does each prebook create an independent hold?

| Question | Answer | Evidence level |
|---|---|---|
| Does Prepare's one-adult prebook create a real hold? | **Yes** — "reserving the offer with the provider". | Documented by provider contract |
| Does the confirmation-time real-party prebook create a second independent hold? | **Yes** — a second `POST /flights/prebooks`. | Documented by provider contract |
| Can both holds coexist? | **Unknown** — the contract does not describe hold interaction. No release call exists, so nothing in the API retires the first. | Unknown without live provider confirmation |
| Does the second prebook invalidate the first? | **No evidence either way.** No documented behaviour. | Unknown |
| Does a successful booking consume/release either hold? | The booking consumes the **booked** prebook. The other is not mentioned. | Documented (booking) / Unknown (first hold) |
| What happens to the first hold after confirmation? | **No documented release.** It is not referenced by any endpoint. | Documented absence |
| What happens when confirmation fails? | The confirm-time prebook is likewise retained; no release call exists. | Documented absence |

**Conclusion:** the prebook is a real provider-side reservation, and LiteAPI
provides **no** API to release, cancel, update, or let it expire on demand.

## 5. Lifecycle alternatives — evaluation

| Alternative | Contract evidence | Decision |
|---|---|---|
| **A. Reuse the first prebook** | No operation accepts passenger data on an existing prebook; `/services` touches only seats/bags. | **Rejected** |
| **B. Update the existing prebook** | No such endpoint. | **Rejected** |
| **C. Release the first prebook** | No prebook cancel/release endpoint; `cancelIntentAt` is "Not applicable to prebook endpoints". | **Rejected** |
| **D. Keep two prebooks** | Precondition is "if the provider requires separate prepare-time and confirmation-time prebooks" — **it does not.** The documented flow is verify → one prebook. | **Rejected as designed** |
| **E. Do not create the first prebook** | `POST /flights/verify` is the documented pre-booking price check and creates no hold. | **Implemented** |

### Final decision (E)

The first prebook is **not required by the contract** and is **unrecoverable**
once created. The provider's own recommended flow obtains the price from
`POST /flights/verify` and creates the prebook exactly once, with the real
traveller party, immediately before booking.

**Change:** `NuiteeFlightBookingProvider.revalidateBooking` at PREPARE time
(no snapshot, no travellers) now calls `verifyOnly()` (`POST /flights/verify`)
instead of `prebookOnce()` (`POST /flights/prebooks`). The review stage already
never prebooked (P3-D7). The confirm stage still prebooks the real party once,
and `createBooking` still only reuses that `prebookId`.

Result: **exactly one prebook per successful logical booking**, created at
confirm with the real party.

## 6. Price changes, failures, retries and timeouts

| Case | Active prebooks after | New prebook? | Previous hold | Idempotency key | Safe retry? | Distinguishable outcome? |
|---|---|---|---|---|---|---|
| Price changes during review | 0 | No | n/a | intact | Yes | Yes — `verify` reports `changes` |
| User accepts the new price | 0 | No | n/a | intact | Yes | Yes |
| Price changes during confirmation | 1 (confirm) | No (retry reuses) | retained | **released** (`price_changed`) | Yes, after re-acceptance | Yes |
| Real-party prebook succeeds, booking fails | 1 | No | retained | released (`failed`) | Yes — retry reuses the prebook | Yes |
| Booking timeout, outcome unknown | 1 | No | retained | released | Yes — `/flights/bookings` is idempotent on `prebookId`, so the retry returns the existing booking if one was created | **Yes** — the retry is safe by contract; the prebook is never recreated |
| User retries confirmation | 1 | **No** (fingerprint match → GET) | retained | new key | Yes | Yes |
| User abandons checkout | 0 | No | n/a | n/a | n/a | Yes |
| Prebook expires before confirmation | 0 or 1 | 1 on retry if the hold is gone | n/a | released | Yes | `GET` returns 404 → fail closed |
| Concurrent confirm submissions | 1 | No | retained | one winner; loser gets `duplicate_request` | Yes | Yes |

No second booking is ever created because a booking response timed out: the
retry reuses the same `prebookId`, and `POST /flights/bookings` is idempotent
on it (documented).

## 7. Code changes and rationale

**`backend/src/modules/bookings/adapters/nuitee-flight-booking.provider.ts`**

1. Added `verifyOnly(offerId)` — read-only prepare-time price check.
2. Prepare path (no context) now returns `verifyOnly(offerId)`; the handoff is
   `{ offerId }` (no `prebookId`).
3. Review path now tolerates a snapshot with **no** `prebookId` (the normal case
   after this change): it only validates a recorded prebook when one exists
   (legacy rows), then verifies. A recorded prebook that fails `GET` still
   fails closed.
4. Confirm path unchanged (one real-party prebook, `travelerFingerprint` reuse
   on retry).

**Rationale:** removes an unavoidable, unrecoverable provider reservation that
the contract neither requires nor provides a release for. No Duffel, hotel,
payment or traveller-validation behaviour is touched.

## 9. Remaining risks and provider limitations

1. **The confirm-time prebook is still an unrecoverable hold on failure or
   abandonment.** LiteAPI has no prebook release endpoint, so a prebook whose
   booking never happens stays with the provider until the provider's own
   (undocumented) expiry. This is inherent to the provider contract and cannot
   be fixed client-side.
2. **Hold expiry is undocumented.** The spec exposes only the offer expiration
   and the services-attachment window; there is no stated prebook TTL or
   auto-release guarantee. Do not assume the hold expires.
3. **Hold interaction is unknown.** Whether two simultaneous prebooks for the
   same offer conflict, and what a successful booking does to a second hold,
   is not documented. After this change the application only ever creates one,
   so the question is moot for new bookings; legacy rows created before this
   change may still carry an orphaned first hold.
4. **No live provider verification.** All hold semantics above are established
   from the OpenAPI specification and the linked guides, not from a live
   sandbox call. Local mock tests prove application behaviour only.
5. **A legacy booking row created before this change** has a `prebookId` in its
   snapshot that is never used (the confirm stage creates a fresh real-party
   prebook). The review stage still validates it when present and fails closed
   if it is gone; those rows cannot be migrated retroactively.
