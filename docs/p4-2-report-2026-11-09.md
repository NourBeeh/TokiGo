## 3. Database schema and migration changes

No new tables and no new columns were needed — the P4-1 schema was already
correct. Two migrations were added:

| # | Name | Effect |
|---|---|---|
| 7 | `P4AttemptStatusStates1731000000007` | Drops `chk_payment_attempts_status`, translates `requires_confirmation` → `requires_action`, adds the P4-2 CHECK. `down()` reverses both. |
| 8 | `P4RetireProcessedWebhooks1731000000008` | `DROP TABLE IF EXISTS processed_webhooks`. `down()` recreates the empty table. |

**Ordering:** 7 then 8, appended after the P4-1 chain. No existing migration was
edited, reordered or deleted.

**Migration 7 ordering matters:** the old constraint is dropped *before* the
translation UPDATE, because writing `requires_action` while the P4-1 CHECK is
still in place violates it. This was found by test M1 and fixed.

**Migration 8 is a real data drop and is justified:** the legacy table stores only
an event id — no provider, no event type, no payload hash — so a faithful backfill
into `webhook_events` is impossible without inventing values. Dropping it does
**not** weaken replay protection, because the effect path is idempotent:

- `succeeded → succeeded` is an identity transition (a no-op);
- the capture ledger key is `capture:{attemptId}`, absorbed by the unique index;
- a redelivery of an event still in `received` is explicitly allowed to retry, so
  a crash before the effect is applied is recoverable.

`down()` restores the table shape but not its rows; a dropped table's contents
cannot be recovered by DDL. This is documented on the migration itself.

**Verified schema after migration:** `payment_attempts` statuses are exactly the
13 P4-2 values (test M2 writes each one); `webhook_events` has `PRIMARY KEY
(provider, "eventId")` (test M3); `processed_webhooks` is absent (M3); the
P4-1 upgrade path preserves rows (M1); migration 7 and 8 round-trip (M4, M5).

## 4. PaymentAttempt state-transition model

```
created ──────────► processing ──────────► requires_action ──┐
                       │                       │             │
                       │                       ▼             │
                       │                    pending ─────────┤
                       │                       │             │
                       ▼                       ▼             ▼
                  requires_action ◄──── processing ◄────── pending
                       │                       │             │
                       ▼                       ▼             ▼
                   succeeded ◄──────────── succeeded ◄─── succeeded
                       │
                       ├──► processing ──► refunded | partially_refunded | unknown
                       ├──► voided
                       └──► consumed                (P4-3)

processing ──► declined | failed | unknown | cancelled
unknown ─────► succeeded | declined | failed | cancelled | processing   (reconciliation only)
partially_refunded ──► refunded | partially_refunded | processing
declined | failed | cancelled | voided | refunded | consumed ──► (terminal)
```

Every state may transition to **itself** — that is how a redelivered webhook or a
retried confirm is a clean no-op instead of an error.

**Rules enforced**

| Rule | Where |
|---|---|
| Invalid moves rejected | `assertTransition()` in `payment-attempt.state.ts`; unit-tested in `payments.state-machine.spec.ts` |
| Atomic transitions | Compare-and-set `UPDATE … WHERE id = ? AND status = <from>`; a losing racer gets `conflict`, never an overwrite |
| No success downgrade | `succeeded` may not reach `pending`/`declined`/`unknown`/`failed`; the only exits are `processing`, `refunded`, `partially_refunded`, `voided`, `consumed` |
| No inferred success | `unknown → succeeded` exists but is reachable only through the webhook path, which re-reads the gateway's authoritative state |
| No client-supplied status | `handleWebhook` derives the target from `gateway.retrievePayment()`, never from `payload.type` |
| Ambiguity is not failure | A thrown gateway error is classified first: definitive refusals → `failed`; anything else (timeout, network) → `unknown`. Never auto-retried, never re-charged |
| Refund safety | `succeeded → processing` exists **only** for the refund path. A definitive refund refusal returns the attempt to its previous state; an ambiguous one goes to `unknown`. `refundPayment` never writes `failed`, so a timeout cannot turn a confirmed success into a failure (test T9) |
| Safe failure detail | Only a fixed code vocabulary is persisted (`payment_not_found`, `amount_exceeded`, `already_refunded`, `invalid_amount`, `not_refundable`, `provider_timeout`, `gateway_error`). The raw provider message is never stored |

**Documented limitation — `cancelled` is unreachable.** The mock gateway exposes
no cancellation operation, so no code path enters `cancelled`. The state exists in
the model and the CHECK so a future gateway can use it without another migration.

## 5. Idempotency and concurrency strategy

**Attempt idempotency** — `UNIQUE ("userId", "idempotencyKey")`, claimed by
`PaymentAttemptService.claim()`:

1. fast-path select;
2. insert;
3. on `23505`, re-select the winner's row.

The database decides the winner of a concurrent race; no check-then-insert window
is relied upon. Four concurrent requests with one key produce exactly one row
(test A3).

**Gateway idempotency keys are namespaced by user** (`"${userId}:${key}"`). A
provider must never hand the same payment intent to two different users who pick
the same client key — that would let one traveller confirm another's payment. The
`(gatewayId, gatewayRef)` partial unique index remains the backstop. Found by
test A4 and fixed.

**Ledger idempotency** — `UNIQUE ("idempotencyKey")`. Keys are deterministic:
`capture:{attemptId}`, `capture-failed:{attemptId}:{confirmKey}`,
`refund:{attemptId}:{refundKey}`. A retry returns the existing row.

**Webhook dedup** — `PRIMARY KEY (provider, "eventId")`, claimed by an explicit
`INSERT` (not `save()`, which upserts and would reset a processed event back to
`received`). `processed`/`ignored` is a hard duplicate; `received`/`failed` may
retry.

**Concurrent updates** — conditional `UPDATE … WHERE status = <from>` for state
changes; `INSERT … ON CONFLICT DO NOTHING` for ledger rows inside the webhook
transaction, so a concurrent writer cannot abort it.

**No open transaction across a network call.** Every operation is: persist/claim
(autocommit) → gateway call (no transaction) → persist the result. The only
explicit transaction in the payment path is the webhook effect, which contains no
gateway call — the gateway is read *before* it.

## 6. CUSTOMER versus SUPPLIER ledger behaviour

`payment_transactions.leg` keeps the two legs apart, and the schema enforces it:

| Leg | Must reference | Never | Enforced by |
|---|---|---|---|
| `CUSTOMER` | `payment_attempts` (`attemptId`) | `providerOperationId` | CHECK `chk_payment_transactions_leg_links` + composite FK `(attemptId, bookingId)` |
| `SUPPLIER` | `provider_operations` (`providerOperationId`) | `attemptId` | same CHECK + composite FK `(providerOperationId, bookingId)` |

- A CUSTOMER transaction records a **capture** only on an authoritative
  `SUCCEEDED`, and a **refund** only on a successful refund. Payment Intent
  creation alone writes nothing (test T7).
- A partial refund records `partially_refunded` on the attempt and a refund row
  for the partial amount; it never marks the whole payment refunded (test T6).
- `bookingBalance()` sums the CUSTOMER leg only, so supplier settlements cannot
  distort the customer's net receipts (test T5).
- A SUPPLIER settlement can exist with no customer attempt at all (test T2), and
  the two legs are never merged on one row.

## 7. Webhook persistence and verification

**`webhook_events` is the single authoritative replay store.** The legacy
`processed_webhooks` table is dropped by migration 8 and its entity removed; no
code path reads or writes it. There is no second mechanism that can disagree.

**Verification is real.** The mock gateway implements HMAC-SHA256 over
`"id:paymentId"` with a constant-time compare (`verifyWebhook`). A bad signature is
rejected **before anything is persisted** (tests W3, W4). No fabricated
verification and no invented provider semantics.

**Order of operations**

1. verify the signature;
2. claim `(provider, eventId)` — insert `received`;
3. read the gateway's **authoritative** state (`retrievePayment`);
4. apply the effect in one transaction: attempt transition + ledger entry +
   `webhook_events.status = 'processed'`;
5. on rejection, mark the event `failed` so a redelivery cannot loop.

**Effects come from the provider, not the client.** `payload.type` selects only
the event-type column and whether the mock's `settlePending` hook runs (and only
for a signature-verified `payment.succeeded`); the resulting state is re-read from
the gateway. A `payment.failed` webhook for a PENDING intent is **not** promoted
to a decline or a success (test W5).

**Documented limitations**

- The mock gateway has no real asynchronous hook; `settlePending` models a bank
  confirming a 3DS intent. A real PSP would settle server-to-server and the
  webhook would only report it.
- The mock gateway cannot model a `payment.failed` transition for a PENDING
  intent, so that case is intentionally left as `pending` rather than invented.
- The mock gateway does not support capture, void or cancellation operations.
  Only `authorize`/`capture`/`refund` semantics that actually exist are used.

## 8. API compatibility impact

`POST /payments/intent`, `/payments/confirm`, `/payments/refund` and
`POST /payments/webhook` keep their **request** contracts — the DTOs are
untouched, so `checkout_payment_service.dart` is unchanged and its tests pass.

| Response | Change |
|---|---|
| `{status:'OK', intent}` | unchanged shape; **additive** `attemptId`, `attemptStatus` |
| `{status:'UNAVAILABLE', reason}` | unchanged |
| `{status:'REJECTED'}` | **additive** `reason` (`invalid_signature`, `duplicate_event`, `unknown_payment`, `unknown_attempt`, `effect_rejected`) |
| `{status:'OK'}` after confirm | **additive** `attemptId`, `attemptStatus` |
| new | `{status:'PENDING'}` when a concurrent request already claimed the attempt; `{status:'UNKNOWN'}` for an ambiguous gateway outcome; `{status:'DECLINED'}` for a declined attempt |

`POST /payments/intent` now **requires the booking to exist and belong to the JWT
user**, and the request currency must equal `bookings.currency`. A violation is a
`404`/`400`; the Flutter client already degrades any non-OK intent response to
`PaymentOutcome.unavailable`, so the flow is not broken.

`GET /payments/ledger/:bookingId` response shape changed (Flutter does not
consume this endpoint — verified by grep over `lib/`):

| Old (in-memory) | New (durable row) |
|---|---|
| `side` | `leg` (`CUSTOMER` \| `SUPPLIER`) |
| `paymentId` | `attemptId` |
| `occurredAt` | `createdAt` (ISO-8601) |
| `gateway` | `gatewayRef` |
| `type: 'CHARGE'` | `type: 'capture'` |
| — | `status`, `providerOperationId`, `providerRef`, `idempotencyKey`, `metadata` |

Added: `GET /payments/ledger/:bookingId/balance` (JWT-guarded) returning
`{charged, refunded, net, currency}` over the CUSTOMER leg.

**No payment proof was added to `POST /bookings`** and the booking confirmation
lifecycle is unchanged — that is P4-3.

## 12. Remaining limitations and risks

1. **`cancelled` is unreachable** with the mock gateway (no cancellation
   operation). The state and CHECK value exist; no code enters it.
2. **The mock gateway has no real async hook.** `settlePending` models bank
   confirmation; a production PSP would settle server-to-server.
3. **`payment.failed` on a PENDING intent is a no-op.** The mock cannot express
   that transition; it is left `pending` rather than invented.
4. **Ledger entries for failed captures are auditable but not reversible.** A
   `declined` attempt keeps its failed-capture row; a retry uses a new attempt
   and a new key.
5. **Ambiguous outcomes require manual reconciliation.** `unknown` is never
   auto-resolved. There is no recovery worker (out of scope for P4-2).
6. **`processed_webhooks` rows are dropped by migration 8** and cannot be
   restored by `down()`. Replay safety is preserved by idempotency, not by the
   old table (see §3).
7. **Dev/prod schema drift for `processed_webhooks`.** Development runs
   `synchronize: true`, which will drop the now-unmanaged table on next boot;
   production drops it via migration 8. Both end in the same state.
8. **Development `synchronize` does not apply migration 7's CHECK** (TypeORM
   does not create CHECKs from the entity). The application-level state machine
   still enforces the vocabulary; production gets the CHECK from the migration.
9. **The concurrent-retry wait is bounded at 1000 ms.** A retry that arrives
   while the winning request is still in flight returns `{status:'PENDING'}` if
   the gateway ref has not landed; the client treats that as unavailable. It
   never triggers a second provider call.
10. **Amount is still the client-quoted checkout total**, validated for
    positivity and currency match — not the raw `bookings.authoritativePrice`,
    because checkout legitimately adds add-ons on top of the offer price. The
    P4-1 entity comment claiming the amount is copied from the booking price was
    corrected.
11. **No supplier-side payment runtime.** `LedgerService.append` supports the
    SUPPLIER leg and it is tested against `provider_operations`, but nothing in
    the booking flow creates supplier settlements yet (P4-3+).
12. **`attemptNo` is computed as `MAX(attemptNo)+1` outside a lock.** Two
    concurrent first attempts for one booking could in principle share a number;
    it is diagnostics-only and unconstrained by design.

## 13. Deployment ordering and migration requirements

1. **Migrations before code.** Deploy with `NODE_ENV=production`
   (`synchronize: false`, `migrationsRun: true`). The app will not boot until
   migrations 7 and 8 have applied, because the runtime repositories require the
   P4-2 CHECK and the absence of the legacy table.
2. **Migration order is fixed:** `…1731000000006` → `1731000000007` →
   `1731000000008`. Never run 8 before 7.
3. **No backfill is required and none should be attempted** — migration 7
   translates the one renamed value; migration 8 drops a table whose contents
   cannot be faithfully reconstructed.
4. **Rollback:** `migration:revert` once removes migration 8 (recreating an empty
   `processed_webhooks`); twice more removes migration 7 (restoring the P4-1
   status vocabulary). Rolling back further is the P4-1 path, unchanged.
5. **Traffic:** the change is backwards-compatible for the Flutter checkout
   (§8), so no coordinated client release is required. The ledger endpoint shape
   changed and must be republished to any non-Flutter consumer.
6. **Dev environments:** a fresh `synchronize` boot will drop
   `processed_webhooks`. Re-running migrations on an existing dev database is
   safe and idempotent (`IF EXISTS` / `IF NOT EXISTS` throughout).
