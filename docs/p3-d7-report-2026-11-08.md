## 2. Original Nuitee review failure and root cause

`POST /offers/revalidate` switched on `dto.providerId` with only two cases
(`duffel-flight`, `nuitee`). `nuitee-flight` fell through to `default`, which
returned:

```json
{ "status": "UNAVAILABLE", "offerId": "…", "reason": "No revalidation path for provider nuitee-flight" }
```

The booking review page's Continue action showed a snackbar and never advanced,
so every Nuitee flight offer was blocked.

**Root cause:** there was no Nuitee flight branch, and the only Nuitee price
source in the adapter was `prebookFlight` — which creates a provider inventory
hold. Adding a naive branch would have raised the hold count to three.

**Provider contract finding (LiteAPI v3.0 OpenAPI reference):** LiteAPI exposes
two READ-ONLY operations that were unused:

| Operation | Endpoint | Creates a hold? |
|---|---|---|
| Verify flight offer | `POST /flights/verify` body `{ offerId }` | No |
| Get prebook | `GET /flights/prebooks/{prebookId}` | No |

Both are documented as pre-booking / resume-checkout reads, not holds.

## 3. Exact revalidation implementation

### 3.1 Provider service (`backend/src/modules/nuitee/nuitee.flight.service.ts`)

- `verifyFlightOffer(offerId)` → `POST /flights/verify`
  - Reads `data[0].journey.pricing.display.{total,currency}` and
    `data[0].journey.expiration`.
  - Reads the provider's own `changes` block: `changes.priceChanged`,
    `changes.pricing.old.display.total`, `changes.pricing.new.display.total`.
  - A non-2xx (404 = offer expired / not found) → `success:false`.
- `getFlightPrebook(prebookId)` → `GET /flights/prebooks/{prebookId}`
  - Same extraction contract as `prebookFlight` (defensive against the
    documented array/object wrapper), plus `journey.pricing.display` fallback.
  - A 404 → `success:false` (prebook gone).

### 3.2 Offer endpoint (`backend/src/modules/offers/offers.controller.ts`)

New `nuitee-flight` branch calling `verifyFlightOffer`:

- success + no price move → `{ status: 'OK', price, currency, expiresAt }`
- `changes.priceChanged` **or** `|knownPrice - verifiedPrice| > 0.01` →
  `{ status: 'PRICE_CHANGED', oldPrice, newPrice, currency, expiresAt }`
- verify failure → `{ status: 'UNAVAILABLE', reason }`

Duffel and hotel branches are untouched.

### 3.3 Booking adapter (`backend/src/modules/bookings/adapters/nuitee-flight-booking.provider.ts`)

`revalidateBooking(offerId, context)` is now stage-aware:

| Stage | Condition | Provider calls | Prebooks |
|---|---|---|---|
| Confirm | travellers present, fingerprint mismatch | `prebookFlight` (real party) | 1 |
| Confirm retry | travellers present, `snapshot.travelerFingerprint` matches | `getFlightPrebook` | 0 |
| Review | snapshot with `prebookId` | `getFlightPrebook` + `verifyFlightOffer` | 0 |
| Review, missing prebookId | snapshot present, no `prebookId` | none | 0 |
| Prepare | no snapshot | `prebookFlight` (sandbox) | 1 |

`createBooking` is unchanged (P3-D6): it reads `offerSnapshot.prebookId` and
calls `/flights/bookings`; it never prebooks.

### 3.4 Contract and service

- `RevalidationContext` gained `offerSnapshot?: Record<string, any>`.
- `BookingsService.revalidate` passes `{ offerSnapshot: booking.offerSnapshot }`.
- `BookingsService.create` passes `{ travelers, offerSnapshot }`.
- The confirm-time handoff now carries `travelerFingerprint` (a JSON
  fingerprint of the mapped passengers + lead contact), persisted in the
  booking snapshot. It is what distinguishes a retry of the same attempt from
  a new party.

## 5. Evidence that confirmation reuses the original prebook ID

- `NuiteeFlightBookingProvider.createBooking` reads `input.offerSnapshot.prebookId`
  and calls `bookFlight({ prebookId, payment })` exactly once. It never calls
  `prebookFlight`.
- A snapshot without a `prebookId` → `success:false` ("Missing Nuitee flight
  prebookId in snapshot") before any provider call.
- An expired/invalid prebook at confirm retry → fail closed; never silently
  re-prebooked.
- Repeated `create` with the same idempotency key → one `bookFlight` call
  (P3-D6 idempotency intact).

## 6. Price and passenger-composition behaviour

- `/offers/revalidate` uses the provider's **own** search-vs-verified
  comparison (`changes`) and also flags a client `knownPrice` mismatch.
- `/bookings/revalidate` returns the live verified price; `BookingsService`
  compares it with `booking.authoritativePrice` and persists
  `previousPrice` / `priceChanged`.
- Confirm compares the real-party prebook price with the stored authoritative
  price. On a move: status `revalidated`, idempotency key released,
  `price_changed` (409) thrown, `authoritativePrice` updated. The client must
  re-accept.
- Flutter shows the price-change banner and blocks Continue until
  `acceptNewPrice`.
- Passenger composition: the prepare-time prebook stays **one adult**
  (traveller identities do not exist at that stage). No identities are
  fabricated. The real party is prebooked once, at confirm.
- Provider limitation retained: the provider cannot validate the complete
  passenger composition before confirmation (the prebook is the only place the
  party exists). The flow is fail-safe — a changed fare blocks confirmation
  rather than being silently accepted.

## 11. Remaining provider limitations

1. **No live provider verification.** Everything above is code inspection plus
   mocked-boundary tests. `POST /flights/verify` and
   `GET /flights/prebooks/{prebookId}` are confirmed against the LiteAPI v3.0
   OpenAPI reference, not a live sandbox call.
2. **The prepare-time Nuitee prebook uses one adult.** A party of a different
   size legitimately surfaces as `price_changed` at confirm (explicit
   acceptance, never a silent charge). Passing the searched party would require
   fabricating passenger identities, which is worse.
3. **The real party's fare is first known at confirm.** Payment is collected
   before that comparison, so a fare move between review and confirm surfaces as
   `price_changed` and requires re-acceptance (fail-safe).
4. **`/flights/verify` prices the searched composition.** The review stage
   surfaces that difference explicitly instead of hiding it.
