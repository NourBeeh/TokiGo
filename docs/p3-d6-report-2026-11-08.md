## 2. Passenger CTA — root cause and fix

### Root cause (confirmed by code inspection)

`_TravelerController.from()` overwrote the document controllers with the form's
empty strings, so `documentType`, `documentIssueCountry` and `documentExpiry`
were always empty while `isValid` required them → the continue button was
permanently blocked.

P3-D5 did **not** fix this. It made `from()` preserve the controller's baseline
values — but those baselines were placeholders (`PASSPORT`, `EG`, `2030-01-01`,
`P123456`) that no UI field could edit. The CTA was therefore "unblocked" by
sending fabricated data to the airline as if it were real.

### Fix applied in P3-D6

- Removed every placeholder. Every field now starts empty.
- Exposed the real fields in the card: document type (dropdown), document
  number, issuing country (ISO), expiry (YYYY-MM-DD).
- Kept the completeness requirement in `_isValid`.

`lib/features/booking/presentation/pages/passenger_details_page.dart`

### Test evidence

- `E1 every document field starts EMPTY` — asserts the controllers are empty and
  no `PASSPORT` / `P123456` text is present.
- `E2 a missing document field keeps the CTA blocked` — clears one document
  field and asserts the route does not advance.
- `B1` (blocked when incomplete) and `B2` (complete card unlocks and persists).

## 4. Duplicate Nuitee prebooking

### Call trace (before)

Three `prebookFlight` calls per logical booking:

1. `BookingsService.prepare` → `revalidateBooking(offerId)` → prebook (sandbox)
2. `BookingsService.create` → `revalidateBooking(offerId)` → prebook (sandbox)
3. `BookingsService.create` → `createBooking` → prebook (real travellers) → book

All three create provider inventory holds. The flow was **not** idempotent.

### Fix applied

- `BookingProvider.revalidateBooking(offerId, context?: RevalidationContext)`
- `BookingsService.create` passes `{ travelers: booking.travelers }`
- `NuiteeFlightBookingProvider.createBooking` reuses `offerSnapshot.prebookId`
  and never prebooks again

### Test evidence

`one logical booking operation creates exactly ONE prebook` — revalidation with
travellers + confirmation → `prebookFlightCalls === 1`, `bookFlightCalls === 1`.

## 5. Duffel passenger-to-offer-ID mapping audit

The `(type, ordinal)` mapping is safe under a validated guarantee: **every offer
passenger is claimed by exactly one traveller**
(`claimed.size === offerPassengers.length`). The offer request passengers are
built adults → children → infants with ages, so the composition is deterministic.

Tested with realistic mocked IDs (`pas_a1`, `pas_c1`, `pas_i1`, …) under:

- Mixed composition: 2 adults + 2 children + 2 infants, traveller order
  deliberately interleaved (infant, adult, child, adult, child, infant) — every
  ID resolves correctly.
- Three adults → three distinct IDs.
- Two children → two distinct IDs.
- Two infants on the same adult → blocked.
- An infant naming a child as its adult → blocked.
- A party smaller than the offer → blocked (`6 passengers but 1 were supplied`).

No ID is invented or inferred from an unrelated array position.

- New explicit field in `ContactForm` and the passenger-details contact block.
- Localized in Arabic and English (`bookingPhoneCountryCodeLabel`,
  `bookingValidPhoneCountryCode`).

- Reaches LiteAPI as `phoneCountryCode` (no `+`) with `phoneNumber` as the

- Duffel receives E.164: `+<code><number>` only when the number has no `+`.

Tests: `F1` missing code blocks, `F2` malformed code blocks, `F3` the code

## 11. Remaining blockers and limitations

1. **No live provider verification.** Everything above is code inspection plus
   mocked-boundary tests. No live Duffel or LiteAPI call was made.
2. **Confirmed defect, not fixed:** `POST /offers/revalidate` has no
   `nuitee-flight` path (default branch returns `UNAVAILABLE`), so the booking
   review page's continue button is blocked for every Nuitee flight offer.
   Fixing it requires a price source that does not create another prebook; adding
   one would raise the hold count to three.
3. **Known limitation:** the prepare-time Nuitee flight prebook uses one adult
   (travellers do not exist at prepare). A party of a different size legitimately
   surfaces as `price_changed` at confirm — safe (never a silent charge), but it
   requires an extra acceptance step. Passing the searched party composition
   would require fabricating passenger identities, which is worse.
4. **Document fields are required in the form for every provider**, because the
   offer's document requirement is not known at form time. The adapter is the
   component that fails closed when the requirement is real.
