## 3. How the authoritative payment amount is derived and validated

### Audit result — where the amount could be influenced

| Stage | Finding |
|---|---|
| Flutter `checkout_page._pay()` | `total = record.authoritativePrice + addOnsTotal` |
| `checkoutAddOnsProvider` | **Always empty.** `add_ons_page.dart` writes `[]` on continue and the page offers nothing to select ("extras are priced by the airline … Until then it offers nothing to select and adds nothing to the total"). So `addOnsTotal` is structurally `0`. |
| `record.authoritativePrice` | Comes from `BookingResponse.authoritativePrice` ← `bookings.authoritativePrice` |
| `bookings.authoritativePrice` / `currency` | Written **only** by provider revalidation (`BookingsService.prepare`, `revalidate`, `create`). `priceBreakdown` is never populated by the backend and `offerSnapshot` holds provider handoff data, not a price authority. |
| `CreatePaymentDto.amount` / `currency` | Client-supplied — **was** the value persisted and charged. |

**Conclusion:** the trustworthy authority already exists and is a single column —
`bookings.authoritativePrice` + `bookings.currency`. No new pricing model was
introduced and no price component was invented. The gap was that the service
trusted the client's copy of it.

### The correction

```
booking row  ──resolveServerPricing()──►  { amount, currency }   ← THE authority
                                              │
client quote  ──assertQuoteMatches()──────►  rejected on mismatch (409)
                                              │
gateway call  ───────────────────────────►  amount/currency sent = authority
                                              │
gateway echo  ──assertGatewayIntentMatches()►  rejected on mismatch → `unknown`
```

1. **Derive.** `resolveServerPricing(booking)` returns
   `{ amount: booking.authoritativePrice, currency: booking.currency }`.
2. **Fail closed when pricing is unverifiable.** `amount` must be a finite
   number `> 0` and `currency` must match `^[A-Z]{3}$`. Otherwise the request is
   rejected with `409 Authoritative pricing/currency is unavailable`. There is no
   fallback to the client quote — a legacy row with `authoritativePrice = 0`
   (the column default) is refused, not guessed at.
3. **Validate the quote.** `assertQuoteMatchesServerPricing` compares the client
   `amount` (within `0.01`, because the column is a Postgres `real`/float32) and
   `currency` against the authority. A mismatch is `409 pricing mismatch`.
   Consequence: a client **cannot** lower or raise the charge, and cannot
   tamper with the currency.
4. **Charge the server value.** The attempt row and the gateway request both use
   `pricing.amount` / `pricing.currency` — never the request values.
5. **Validate the provider echo.** `assertGatewayIntentMatches` runs on the
   `createPaymentIntent`, `confirmPayment`, `refundPayment` and webhook
   `retrievePayment` results. A contradiction is a
   `GatewayAmountMismatchError`; the attempt is moved to `unknown` with
   `failureCode = gateway_amount_mismatch` and **no capture is recorded**. A
   provider state that contradicts the durable attempt is an ambiguity, never a
   success.
6. **Bound refunds.** A refund must be `> 0` and `<= attempt.amount`
   (within tolerance), so a refund can never exceed what was captured.
7. **Currency** is validated against the booking on every path; `refundPayment`
   takes its currency from the attempt, not the request.

### Compatibility

The Flutter client sends exactly `record.authoritativePrice` and
`record.currency`, so every legitimate request matches and behaves exactly as
before — verified by AA8 and by the unchanged Flutter payment tests. The DTO
gains no field and loses none.

### Remaining limitation

If add-ons ever become real (the feed is not connected), the client's total will
legitimately exceed `bookings.authoritativePrice` and this check will reject it.
That is the correct safe behaviour for the current architecture — the booking row
has no add-on component — and it is documented rather than papered over by
inventing a price model.

## 4. How legacy webhook records and replay protection are preserved

### Decision: keep the legacy table, check both stores

A faithful backfill into `webhook_events` is impossible **without inventing
data**: the legacy table stores only a bare event id — no provider, no event
type, no payload hash. Fabricating a provider value would change what the
historical rows mean, which P4-2R explicitly forbids.

So the legacy table is retained as an **archive + compatibility source**:

| Store | Role | Identity |
|---|---|---|
| `webhook_events` | authoritative for events first seen after P4-2 | `(provider, eventId)` — unchanged |
| `processed_webhooks` | **retained archive**; checked before any effect and written for every event, so it cannot drift | bare `id` — the **original** semantics, deliberately not modernised |

`processed_webhooks` keeps exactly its original shape (`id` PK + `processedAt`,
no provider column) — test M3 asserts the columns and the primary key, so a
future "modernisation" that invents a provider column fails the suite.

### Handler flow

```
signature verify
      │
      ▼
legacy lookup ──found──► REJECTED duplicate_event_legacy      (no effect at all)
      │not found
      ▼
claim (provider, eventId) in webhook_events ──duplicate──► REJECTED
      │fresh / retry
      ▼
read authoritative gateway state
      │missing ──► mark ignored + archive id ──► REJECTED unknown_payment
      ▼
find attempt by gatewayRef
      │missing ──► mark ignored + archive id ──► REJECTED unknown_attempt
      ▼
amount/currency must match the attempt ──else──► mark failed + archive id ──► REJECTED
      ▼
transaction: attempt transition + ledger + webhook_events.processed + legacy archive id
      │failure ──► mark failed + archive id ──► REJECTED effect_rejected
      ▼
PROCESSED
```

The legacy archive id is written with `INSERT … ON CONFLICT DO NOTHING`, inside
the same transaction as the financial effect where there is one — so the two
replay stores commit together and a concurrent duplicate can never abort the
effect.

Because the archive is now also written for new events, a redelivery can be
caught by either store; the reason distinguishes them (`duplicate_event_legacy`
vs `duplicate_event`).

## 5. Migration behaviour for databases that already applied P4-2

**Editing migration 8 is safe here, and it is not the mechanism that fixes
already-migrated databases.**

| Database state | What happens | Rows |
|---|---|---|
| Never applied P4-2 (includes every dev DB — dev runs `synchronize`, so migrations never ran) | corrected migration 8 `up()` is a no-op; migration 9 is `CREATE TABLE IF NOT EXISTS` → no-op | **preserved** (M6 proves it end-to-end) |
| Applied the **original** migration 8 (table dropped) | TypeORM has migration 8 recorded, so its corrected `up()` will **not** re-run. Migration 9 runs and recreates the table **empty**. | **already lost** — no DDL can recover a dropped table's rows |
| Applied the corrected migration 8 | migration 9 no-op | preserved |

Migration 9 exists precisely because "edit the already-applied migration" is not
a fix — TypeORM records migrations by name and never re-runs them. M7 simulates
the damaged state (drop the table, revert migration 9 so it is pending, re-apply)
and asserts the archive comes back in the exact shape the entity maps.

**This is an honest, documented loss, not a hidden one.** No database outside
this repository has applied P4-2, and production was never touched.

## 6. Rollback behaviour and limitations

- `migration:revert` once → reverts migration 9 (`down()` is a no-op).
- twice → reverts migration 8 (also a no-op).
- **The archive is never dropped by any up or down path.** M4 asserts the table
  survives a full 9 → 8 revert and re-apply.

Limitations:

1. **Databases that ran the original drop have permanently lost their historical
   event ids.** Migration 9 recreates an empty archive. Replay safety for those
   specific ids is gone; the idempotent state machine still prevents a replayed
   *success* from moving money twice (identity transition + unique ledger key),
   but the replay will be *processed* rather than refused.
2. **Legacy identity is id-only.** A post-P4-2 event whose id collides with a
   legacy id is rejected as a legacy duplicate, even from a different provider.
   That is the original table's semantics, preserved on purpose.
3. **Migration 9 must be applied before the P4-2R code serves traffic.** If the
   archive table is missing, the legacy lookup/insert fails and the webhook
   effect rolls back (the event stays `received` and retries). Production runs
   migrations on boot (`migrationsRun: true`); development creates the table via
   `synchronize` from the restored entity.
4. **If add-ons become real, the amount check in §3 must be revisited** (see the
   limitation in §3).

   treated as a legacy duplicate. Original semantics, preserved deliberately.

   has no add-on component; the check fails closed rather than inventing one.

5. **`cancelled` remains unreachable** with the mock gateway (unchanged from
   P4-2 — no cancellation operation exists).
6. **`payment.failed` on a PENDING intent is still a no-op** with the mock
   gateway (unchanged from P4-2).
7. **Ambiguous outcomes still require manual reconciliation**; no recovery
   worker was added (out of scope).
