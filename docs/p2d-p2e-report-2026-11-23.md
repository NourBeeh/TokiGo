## 2. Audited provider contracts

The audit was performed independently for each provider. Nuitee was **not**
assumed to match Duffel, and no field was inferred from the other provider.

### Duffel API v2

Audited surfaces: Offer Requests, Offers, offer expiry/retrieval, slices,
segments, carriers, fare brands, baggage, and refund/change conditions.

Documented fields used:

- `slices[].comparison_key` — the documented slice identity primitive. It is
  retained as **metadata**, never used as the sole itinerary key.
- `slices[].segments[]` — ordered segments with:
  - `origin.iata_code`, `destination.iata_code`
  - `departing_at`, `arriving_at`
  - `marketing_carrier`, `marketing_carrier_flight_number`
  - `operating_carrier`, `operating_carrier_flight_number`
  - `stops`
- `slices[].fare_brand_name` — nullable; mixed slice brands have no single
  honest top-level brand.
- `slices[].segments[].passengers[].baggages[]` — `type` (`carry_on` or
  `checked`) and `quantity`.
- `conditions.refund_before_departure` and
  `conditions.change_before_departure` — tri-state:
  `allowed`, `penalty_amount`, `penalty_currency`. A null condition means
  **unknown**, never "not allowed".
- Offer expiry only when the provider sends it; never fabricated.

Offer-level conditions are authoritative. Slice-level conditions are used only
when every slice agrees.

### Nuitee / LiteAPI Flights API v3.0

Audited surfaces: flight search, verify, prebook, and book.

Documented fields used:

- Search response: `data[].journeys[]`; each `FlightJourney` carries complete
  ordered `segments[]`, `offers[]`, `totalDuration`, and `connections`.
- `journeyKey` — documented as a hash of route, flights, and times. It is
  retained as **metadata**, never used as the sole itinerary key.
- Offer: `offerId` (verbatim), `expiration`, `pricing.display`
  (`base`/`taxes`/`fees`/`total`), `fare.family`, `mixedCabin`,
  `mixedFareFamily`, `seatsRemaining`.
- Terms: `terms.refundable`, `terms.changeable`, `terms.summary`,
  `terms.changeFee`, `terms.refundFee`, `terms.hasChangeFee`,
  `terms.hasRefundFee`.
- Baggage: `baggage.included[]` with `bagType` (`cabin`/`checked`/`equipment`),
  `pieces`, `weightKg`, `description`, `passengerType`.
- Per-segment fare/amenity: `segmentFares` (`cabin`, `fareBasisCode`) and
  `segmentAmenities` (`aircraftType`).
- Segment: `originCode`, `destinationCode`, `departureTime`, `arrivalTime`,
  `carrier.marketingCode`/`marketingName`/`operatingCode`/`operatingName`,
  `flight.marketingNumber`/`operatingNumber`, `segmentKey`, `stopCount`/`stops`,
  `duration`, `direction`.
- `searchId` — retained for the booking handoff.

Endpoints:

- Verify: `POST /flights/verify` — read-only, `offerId` only.
- Prebook: `POST /flights/prebooks` — documented inventory hold.
- Book: `POST /flights/bookings`.
- A 404 means the offer expired.

### Contract separation

Duffel and Nuitee each have their own mapper and booking adapter. The shared
layer consumes a normalized offer shape; it never copies a Duffel-only field
into Nuitee (or vice versa), never mixes provider offer IDs, and never uses one
provider's key as another provider's identity.

## 3. Defects found and root causes

### Phase 2D

1. **One card per provider offer, not per itinerary.** Search aggregation
   returned every offer as its own row, so identical itineraries appeared
   multiple times and fare variants had no home. Root cause: no grouping stage
   between provider results and the response.
2. **No canonical itinerary identity.** Grouping on origin/destination alone
   would merge different flights. Root cause: no normalized ordered-segment
   identity. Fixed with the key described in §4.1.
3. **Duffel conditions were treated as boolean.** A null condition could be
   read as "not allowed". Root cause: missing tri-state modeling. Fixed:
   unknown stays null; slice fallback only when every slice agrees.
4. **Nuitee mapping omitted documented facts.** Segments, marketing/operating
   carriers, fare basis, terms, baggage, and mixed-cabin flags were not
   normalized. Root cause: a thin mapper. Fixed per the audited contract.
5. **Malformed client offers were fabricated into bookable rows.** Missing
   price/currency/departure/arrival became `USD` or `DateTime.now()`. Root
   cause: permissive client mapping. Fixed: malformed offers are dropped.
6. **Nuitee flight revalidation could report success without a usable price.**
   Root cause: no fail-closed guard. Fixed: missing/non-positive price or
   missing currency returns `UNAVAILABLE` / `Provider returned no usable price`.
7. **Mixed fare brands could be shown as one brand.** Root cause: no
   mixed-brand handling. Fixed: a single top-level brand is exposed only when
   the provider proves one; otherwise it stays null.
8. **Offer-level baggage could overstate a segment's allowance.** Root cause:
   no conservative aggregation. Fixed: the offer-level allowance is the
   conservative minimum across segments; unknown stays unknown.
9. **Duplicate provider offers could appear twice.** Root cause: no dedupe
   inside a group. Fixed: duplicate `(providerId, offerId)` within one itinerary
   is dropped (first wins); the same provider+id in different itineraries is
   never silently merged.

### Phase 2E

10. **Price changes were visible but not an acceptance gate.** Checkout could
    charge before a final check, and a confirm-time change produced a generic
    failure. Root cause: no shared, binding acceptance state.
11. **Terms changes were invisible.** Only price was compared. Root cause: no
    normalized terms snapshot or version. Fixed with `OfferTermsSnapshot` and a
    deterministic `terms-v1-<sha256>` version.
12. **Acceptance was not bound to the exact offer.** A stale screen could accept
    a price that had already moved again. Root cause: no signature validation.
    Fixed: acceptance binds `providerId + offerId + currentPrice + currency +
    termsVersion`; stale signatures are rejected.
13. **Repeated revalidation overwrote the originally accepted price.** Root
    cause: acceptance state replaced on every check. Fixed: the accepted
    baseline is preserved across pending changes and cleared on any detected
    change.
14. **Declines were not persisted or auditable.** Root cause: no decision
    record. Fixed: decisions are stored in the existing JSONB metadata and
    written to `audit_logs`.
15. **The client surfaced the raw JSON envelope.** Root cause:
    `bookingErrorFrom` preferred `error.message` wholesale. Fixed: the backend
    body's human `message` is preferred; structured `details` are preserved.

## 4. Phase 2D — grouping and fare preservation

### 4.1 Grouping identity definition

The canonical key is derived from the itinerary itself, never from a
provider-specific hash alone and never from origin/destination alone.

Ordered segments; each segment contributes:

- origin
- destination
- departure instant
- arrival instant
- marketing carrier code
- marketing flight number
- operating carrier code
- operating flight number
- technical stop count (`null` is distinct from `0`)

The key is:

```text
flight-itinerary:v1|<segment-1>||<segment-2>|...
```

with segment fields joined by `~`.

Normalization is conservative:

- Instants are normalized without conversion. An offset (`Z`, `+02:00`,
  `+0200`) is preserved. An offset-bearing instant and the same local clock
  text without an offset remain **different**; they are not provably the same
  moment.
- Equivalent spellings (`16:10` and `16:10:00.123`) normalize to the same
  moment.
- A missing field is never guessed.

Excluded from the key on purpose:

- cabin class
- fare brand

These are fare variants of the same itinerary, not different itineraries.

If any segment's identity cannot be proven, the offer gets its own singleton row
keyed by `flight-offer:<providerId>:<id>` instead of being merged into a group
it may not belong to.

Provider keys (`comparison_key`, `journeyKey`) are retained as metadata only.

### 4.2 Proof that every valid offer is preserved

- The raw provider buckets in `successes` are left untouched. Grouping adds a
  top-level `results` array; it does not delete or rewrite the raw offers.
- Each grouped row contains:
  - `offers` — every valid offer for that itinerary, cheapest-first;
  - `offerCount`;
  - `providerIds`;
  - `providerOfferIds`;
  - the summary offer's exact `id` and `providerId` at the row level.
- Every nested offer retains its original `id`, `providerId`, `providerName`,
  price, currency, fare brand, cabin, baggage, and conditions.
- Invalid offers are excluded from `results` and counted in
  `invalidOffersDropped`. They are not replaced with fabricated data.
- Duplicate `(providerId, offerId)` pairs inside one group are counted in
  `duplicatesDropped`; the first valid offer wins.
- The same `(providerId, offerId)` appearing in different itinerary groups is
  **not** silently merged.
- Cross-provider offers are grouped only when their normalized ordered-segment
  identities match exactly. Unprovable timezone/format differences stay
  separate.

The 36-test grouping suite proves these invariants, including:

- identical ordered segments across providers grouped with every exact offer;
- different connection airports kept separate;
- different operating carriers (codeshares) kept separate;
- different segment order kept separate;
- different departure/arrival times kept separate;
- offset-bearing vs offset-less instants kept separate;
- different technical stop counts kept separate;
- cabin/fare-brand variants grouped into one row with every fare;
- duplicate provider+offer IDs deduped inside a row;
- the same provider+id across different itineraries not merged;
- lowest effective customer amount chosen as the summary;
- amounts in different currencies never falsely ranked;
- deterministic ordering for equal prices;
- invalid offers dropped and counted;
- unprovable itineraries kept as singletons;
- Duffel mapping of ordered segments, both carriers, baggage, conditions, and
  stop counts;
- Duffel offer-level conditions authoritative, slice conditions only when all
  slices agree;
- Nuitee mapping of ordered legs, carriers, fare facts, baggage, and terms;
- Nuitee weight-only baggage kept as weight, not a fabricated piece count;
- Nuitee `mixedCabin`/`mixedFareFamily` honored instead of choosing one leg;
- no fabricated expiry or airline.

### 4.3 Client presentation

- One card per grouped itinerary. The card's summary price is the lowest
  qualifying offer.
- `FlightOffer` now carries `segments`, nested `offers`, typed `conditions`,
  typed `baggageAllowances`, and computed getters (`refundable`, `changeable`,
  `fareBrand`, `selectableOffers`) with fallbacks to existing metadata.
- `withSummary` replaces only the row summary while preserving every grouped
  fare.
- Filters evaluate each offer in a group and keep the row when at least one
  offer qualifies; the row summary is then set to the lowest qualifying offer
  while `offers` retains all fares.
- Price facets and airline facets span individual offers, not only row
  summaries.
- The details page keeps `_selectedFlightOffer` and shows a fare selector for
  every valid fare, with cabin, baggage, fare brand, refundability, change
  conditions, restrictions, and total only when the provider supports them.
  Unknown stays unknown.
- The booking handoff uses the selected offer's exact ID and provider; the
  selected fare is never silently replaced.

## 5. Phase 2E — shared price/terms-change confirmation

### 5.1 Backend

- New `backend/src/common/pricing/offer-terms.ts`:
  - `OfferTermsSnapshot` — normalized terms;
  - `canonicalJson` — deterministic serialization;
  - `termsVersionOf` — `terms-v1-<sha256>`;
  - `diffOfferTerms`, `termsFromNormalizedFlightOffer`,
    `termsFromChangedFlags`, `priceDifference`, `priceChangePercent`.
- `BookingRevalidation` carries optional `terms`, `termsVersion`, and
  `changedTerms`.
- Provider adapters pass normalized terms through:
  - Duffel live offer via `mapDuffelOffer`;
  - Nuitee flight verify via the mapped offer plus `changes.*Changed` flags;
  - Nuitee hotel prebook via the documented `cancellationChanged` /
    `boardChanged` true flags.
  Missing terms stay absent; no defaults.
- `BookingsService`:
  - `prepare` stores the selected state as accepted and records the baseline in
    the existing `providerMetadata` JSONB (`priceRevalidation`,
    `priceAcceptance`, `priceChangeDecision`). No new DB columns or migrations.
  - `revalidate` compares the live price and terms against the accepted state,
    preserves the original accepted price across repeated changes, clears
    acceptance on any change, and returns a structured `priceChange`.
  - `create` rejects any pending change or missing acceptance with
    `price_changed`, frees the idempotency key, and preserves metadata.
  - `decidePriceChange` accepts or declines with stale-signature validation and
    writes an audit entry.
  - `toResponse` includes `priceChange`; confirm merges provider metadata
    instead of replacing it.
- New endpoint: `POST /bookings/:id/price-change`, with optional
  `expectedPrice`, `expectedCurrency`, and `expectedTermsVersion` to reject
  stale screens.
- Audit decisions are written to the existing `audit_logs` table via the
  optional `AuditLog` repository; no new payment models.
- `offers.controller.ts` `/offers/revalidate` was enhanced with `providerId`,
  `offerType`, `priceDifference`, `priceChangePercent`, `priceChanged`,
  `termsChanged`, `terms`, `termsVersion`, `changedTerms`, `checkedAt`,
  `previousPrice`, and `currentPrice`. `PRICE_CHANGED` is returned for both
  price-only and terms-only changes, with `priceChanged`/`termsChanged` flags.

Wire shape of `priceChange`:

- `providerId`, `offerId`, `offerType`
- `previousPrice`, `currentPrice`, `currency`
- `priceDifference`, `priceChangePercent`
- `priceChanged`, `termsChanged`, `changedTerms`
- `previousTerms`, `currentTerms`, `termsVersion`
- `requiresAcceptance`, `accepted`, `decision`, `checkedAt`

### 5.2 Client

- New `lib/features/booking/domain/price_change.dart`:
  - `PriceChangeConfirmation.tryParse` rejects payloads without an exact
    identity, usable positive price, currency, or terms version;
  - missing previous price/percent/terms stay null;
  - `acceptancePayload` binds the decision to the shown amount, currency, and
    terms version.
- `BookingRecord` carries `priceChange`; the repository maps it; legacy records
  without one stay null (never synthesized).
- `BookingRepository` remains backward-compatible: `decidePriceChange` lives in
  a separate `PriceChangeDecisionRepository`; `BookingRepositoryImpl`
  implements both.
- `BookingController`:
  - revalidation consumes the backend-owned `record.priceChange`;
  - `acceptNewPrice` / `declinePriceChange` are async and trust the backend;
  - the confirm gate refuses a pending change;
  - a confirm-time `price_changed` parses `details.priceChange` and returns to
    review instead of showing a generic failure.
- Review page:
  - uses only `BookingController.revalidate` → `POST /bookings/revalidate`;
  - shows the shared banner with previous price, updated price, difference and
    percentage, currency, and changed conditions;
  - explicit **Update price** and **Decline** actions;
  - decline returns to offer selection with no booking at the changed price;
  - unavailable/expired explains the situation and asks for another offer;
  - a declined banner is shown;
  - no-charge note is shown while a change is pending.
- Checkout page:
  - revalidates the prepared booking immediately before charging;
  - a price or terms change returns to review without charging or booking;
  - an unavailable offer does not charge;
  - a confirm-time price change returns to review.
- `bookingErrorFrom` prefers the backend body's human `message` over the raw
  JSON envelope and preserves structured `details`.
- New l10n keys cover Update price, Decline, Choose another offer, declined
  message, Previous price, Updated price, Difference, Conditions changed,
  no-charge note, and term labels. Generated l10n files were regenerated.

### 5.3 Acceptance binding and audit

Acceptance is bound to:

```text
providerId + offerId + currentPrice + currency + termsVersion
```

Any subsequent change to price, currency, or terms invalidates the acceptance
and requires a new explicit decision. The decision is stored with the booking
and written to the audit log with the old price, new price, decision, timestamp,
and offer identity.

No provider price hold is assumed. Duffel offer retrieval and Nuitee flight
verify are read-only. Nuitee's documented prebook hold is used only where the
hotel booking contract already requires it.

## 9. Separate Duffel vs Nuitee contract verification

| Concern | Duffel v2 | Nuitee Flights v3.0 | Shared normalization |
| --- | --- | --- | --- |
| Itinerary identity | `slices[].comparison_key` (metadata); ordered `slices[].segments[]` | `journeyKey` (metadata); ordered `segments[]` | Canonical key from ordered segment fields (§4.1) |
| Marketing vs operating carrier | Separate carrier objects and flight numbers | `carrier.marketingCode`/`operatingCode`, `flight.marketingNumber`/`operatingNumber` | Both preserved; never collapsed into one |
| Times | `departing_at`, `arriving_at` | `departureTime`, `arrivalTime` | Normalized without conversion; offsets preserved |
| Refund/change | `conditions.*_before_departure` tri-state | `terms.refundable`/`changeable`, fee fields, `has*Fee` | Tri-state; null stays unknown |
| Baggage | `slices[].segments[].passengers[].baggages[]` | `baggage.included[]` with `bagType`, `pieces`, `weightKg` | Typed allowances; conservative minimum; weight-only stays weight |
| Fare brand | `slices[].fare_brand_name` | `fare.family`, `mixedCabin`, `mixedFareFamily` | Single brand only when proven; mixed → null |
| Expiry | `expires_at` only when sent | `expiration` only when sent | Never fabricated |
| Revalidation | Live offer fetch (read-only) | `POST /flights/verify` (read-only) | Fail closed on missing price/currency |
| Booking | Duffel adapter | Prebook + book adapters | Separate provider adapters |

**Mocked vs live:** every provider-contract test in this report uses fixtures
or fakes. The mappings were verified against the audited documentation and
fixtures; no live Duffel or Nuitee response was fetched, and no live booking,
hold, or payment was made.

**Known limitations (honest):**

- Duffel `comparison_key` and Nuitee `journeyKey` are retained as metadata, not
  used as the sole identity. This is deliberate: cross-provider grouping needs a
  canonical key.
- Cross-provider grouping requires exact normalized segment identity. Unproven
  timezone/format differences remain separate rather than risk a false merge.
- Baggage is the conservative minimum across segments; an unstated segment
  allowance stays unknown instead of being inferred.
- Mixed fare brands/cabins have no single top-level value; the fare selector
  exposes each variant.
