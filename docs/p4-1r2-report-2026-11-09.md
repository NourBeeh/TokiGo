## 3. Trigger logic and protected update cases

`p4_protect_selected_provider()` is now a **`BEFORE UPDATE` row trigger on `providers`**
(`trg_protect_selected_provider`). It runs for every UPDATE and computes:

```sql
v_protected = EXISTS (
  SELECT 1 FROM provider_selection
  WHERE "providerKey" IN (OLD."providerKey", NEW."providerKey")
);
```

If — and only if — the row is protected, it rejects:

| Case | Condition | Error |
|---|---|---|
| Identity change | `NEW."providerKey" IS DISTINCT FROM OLD."providerKey"` | providerKey cannot be changed |
| Vertical change | `NEW.vertical IS DISTINCT FROM 'flight'` | vertical cannot change away from flight |
| Deactivation | `NEW."isActive" IS DISTINCT FROM true` | cannot be deactivated |

Design points:

- **Direct SQL covered.** It is a database trigger, not application validation.
- **Unrelated fields allowed.** `name`, `priority`, `healthStatus`, `latencyMs`,
  `lastCheckedAt`, `config`, … never raise.
- **Multi-column statements handled.** Because the trigger checks OLD vs NEW per row,
  a single `SET vertical='hotel', "isActive"=false, name='x'` is rejected.
- **No update-ordering loophole.** Checking both `OLD` and `NEW` keys means a row that
  *becomes* the selected provider is protected too — a transaction cannot first re-point
  `provider_selection` and then mutate the old row, or mutate a row into the selected key.
- **Transactions safe.** `BEFORE UPDATE` sees both row versions; a raise aborts the whole
  transaction.
- **Clear errors.** Each case names the provider and the blocked operation.
- **Whitelist / uniqueness / zero-selection preserved.** The `providerKey` CHECK, the
  `uq_one_active_flight_provider` partial unique index, and the empty-selection state are
  untouched. Clearing the selection first makes all protected changes legal again
  (test 3k).

## 4. Rollback validation policy and failure behaviour

`p4_provider_status_backup` now stores two columns per real flight provider:

- `originalIsActive` — the pre-migration state (what `down()` restores).
- `migrationIsActive` — the **exact** state migration 6 produces (what `down()` requires).

`migrationIsActive` is computed with a `CASE` that mirrors the reconciliation precisely
(kept provider stays active; other active real flight rows become inactive; inactive or
non-flight rows are untouched).

`down()` runs a `DO` block **before any destructive operation**:

1. `LEFT JOIN providers` → if any backed-up provider row is missing, abort with
   `provider_selection rollback aborted: required provider row(s) missing: …`.
2. `JOIN providers` → if any provider's live `isActive` differs from
   `migrationIsActive`, abort with
   `provider_selection rollback aborted: provider status changed after migration 6 for: …`.

Only after both checks pass does it drop the triggers, functions and index, restore
`originalIsActive`, and drop the backup table and `provider_selection`.

Because TypeORM wraps `undoLastMigration()` in a transaction, a failed rollback leaves the
migration record, triggers, index, selection table, backup rows and provider state exactly
as they were. A successful rollback restores the original states; re-applying the
migration recreates the backup from the restored state, so it is deterministic.

## 8. Remaining limitations / risks

1. **Protection covers UPDATE only.** `DELETE` of a selected provider is already blocked
   by the `provider_selection` FK; `INSERT` of a duplicate `providerKey` is blocked by
   its unique constraint. No gap.
2. **`migrationIsActive` assumes the reconciliation rules.** The `CASE` mirrors the
   reconciliation exactly; if the reconciliation logic changes later, the backup
   computation must change with it.
3. **`p4_provider_status_backup` persists while migration 6 is applied.** It is
   migration-owned and must never be edited by application code; `down()` drops it.
4. **Development schema divergence (unchanged, documented).** Development `synchronize`
   does not create the flight-provider exclusion index or the ownership FK — those remain
   migration-managed and authoritative for production.
5. **`processed_webhooks` vs `webhook_events`** and the other P4-2 items from the P4-1
   report remain unchanged (out of scope).
