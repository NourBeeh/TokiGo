## 3. Entity relationships and constraints

```
bookings ──────────────< payment_attempts
  │  id (PK)              │ bookingId (FK)
  │  paymentAttemptId ────┤ userId
  │  paymentStatus        │ idempotencyKey   UNIQUE (userId, idempotencyKey)
  │  consumedAt           │ amount / currency / status
  │  confirmingSince      │ gatewayId / gatewayRef
  │  confirmingOwner      │ consumedAt
  │  legacyUnverified     └ UNIQUE (id, bookingId), UNIQUE (id, userId)
  │  version
  │
  ├─────────────────────< provider_operations
  │                        │ bookingId (FK)
  │                        │ providerId / operation / providerRef
  │                        │ idempotencyKey  UNIQUE (providerId, idempotencyKey)
  │                        │ status / startedAt / completedAt
  │                        └ UNIQUE (id, bookingId)
  │
  ├─────────────────────< payment_transactions
  │                        │ bookingId (FK, mandatory)
  │                        │ attemptId (FK, nullable)          → CUSTOMER only
  │                        │ providerOperationId (FK, nullable)→ SUPPLIER only
  │                        │ leg CHECK (CUSTOMER|SUPPLIER)
  │                        │ leg-links CHECK (mutually exclusive)
  │                        │ type / status / amount / currency
  │                        │ gatewayRef / providerRef
  │                        │ idempotencyKey UNIQUE
  │                        └ composite FKs (attemptId,bookingId) and
  │                           (providerOperationId,bookingId)
  │
  └─────────────────────< webhook_events  (provider, eventId) PK

providers ──────────────< provider_selection
  │ providerKey (UNIQUE)   │ selectionKey PK CHECK = 'flight'  (singleton)
  │ isActive / vertical    │ providerKey (FK)
  │ isFallback / priority  │ selectedAt / selectedBy
  └ UNIQUE partial index (vertical) WHERE flight + active + key IN
    ('duffel-flight','nuitee-flight')
```

**Key constraints**

| Constraint | Where | Guarantees |
|---|---|---|
| `UNIQUE (userId, idempotencyKey)` | `payment_attempts` | idempotency is per **user**, not per booking |
| no `UNIQUE (bookingId, userId)` | `payment_attempts` | many attempts per booking are allowed |
| `UNIQUE (paymentAttemptId) WHERE NOT NULL` | `bookings` | one attempt cannot be consumed by two bookings |
| single scalar `paymentAttemptId` column | `bookings` | a booking cannot hold two consumed attempts |
| composite FK `bookings(paymentAttemptId, id) → payment_attempts(id, bookingId)` | migration 3 | consumed attempt belongs to **this booking** |
| composite FK `bookings(paymentAttemptId, userId) → payment_attempts(id, userId)` | migration 3 | consumed attempt belongs to **this user** |
| `CHECK` leg links | `payment_transactions` | CUSTOMER ⇒ attempt set / operation null; SUPPLIER ⇒ operation set / attempt null |
| composite FKs `(attemptId,bookingId)`, `(providerOperationId,bookingId)` | `payment_transactions` | no cross-booking financial reference |
| `UNIQUE (idempotencyKey)` | `payment_transactions` | one financial effect per key |
| `UNIQUE (providerId, providerRef) WHERE NOT NULL` | `provider_operations` | provider-reference uniqueness scoped to the provider |
| `UNIQUE (providerId, idempotencyKey)` | `provider_operations` | one operation per provider per key |
| `PRIMARY KEY (provider, eventId)` | `webhook_events` | durable replay protection |
| `UNIQUE (vertical) WHERE flight + active + key IN (...)` | `providers` | at most one active real flight provider |
| `PRIMARY KEY (selectionKey)` + `CHECK (selectionKey='flight')` | `provider_selection` | singleton selection record (0 or 1 row) |
| `CHECK (amount >= 0)`, `CHECK (currency ~ '^[A-Z]{3}$')` | attempts / transactions | sane financial values |

## 5. Backfill behavior

Migration 3 adds the new `bookings` columns with safe defaults
(`legacyUnverified = false`, `paymentStatus = 'unverified'`) and then runs a
**one-time** backfill:

```sql
UPDATE bookings
SET "legacyUnverified" = true,
    "paymentStatus" = 'legacy_unverified'
WHERE "paymentAttemptId" IS NULL;
```

- Every booking that existed before P4-1 has no verifiable payment proof → marked
  `legacy_unverified` / `legacyUnverified = true`.
- **No** `PaymentAttempt` and **no** `PaymentTransaction` is fabricated. The test
  asserts both tables stay empty after backfill.
- New bookings created after the migration get `legacyUnverified = false` /
  `paymentStatus = 'unverified'`.
- The in-memory `paymentOwners` / `bookingOwners` maps and the in-memory ledger are
  **not** recoverable and are not reconstructed. Ownership is re-derived from
  `bookings.userId` / `payment_attempts.userId` in P4-2+.

Test 2 proves this by rebuilding a pre-P4-1 `bookings` table, inserting a confirmed
booking, applying the chain, and asserting `paymentStatus = 'legacy_unverified'`,
`legacyUnverified = true`, `paymentAttemptId = NULL`, and zero payment rows.

## 6. How customer and supplier transactions are separated

`payment_transactions.leg` is `CUSTOMER` or `SUPPLIER`, and the CHECK
`chk_payment_transactions_leg_links` makes the two legs mutually exclusive:

- **CUSTOMER** — `attemptId` **must** be set, `providerOperationId` **must** be null.
  The composite FK `(attemptId, bookingId) → payment_attempts(id, bookingId)` makes a
  cross-booking customer transaction impossible.
- **SUPPLIER** — `providerOperationId` **must** be set, `attemptId` **must** be null.
  The composite FK `(providerOperationId, bookingId) → provider_operations(id,
  bookingId)` makes a cross-booking supplier settlement impossible.

A supplier settlement therefore exists with **no** customer attempt (test 10), and a
customer transaction can never be recorded without its matching attempt (test 11a).
The two legs are never mixed on one row.

## 7. How payment attempts are protected against cross-booking consumption

1. **Idempotency per user** — `UNIQUE (userId, idempotencyKey)` on `payment_attempts`.
   A retried request cannot create a second attempt for the same logical payment even
   if it points at a different booking (test 4).
2. **Many attempts per booking** — there is no `UNIQUE (bookingId, userId)`; a decline
   is just another row (test 3).
3. **One attempt → one booking** — the partial unique index
   `uq_bookings_payment_attempt` on `bookings.paymentAttemptId` means a second booking
   cannot reference the same attempt (test 5).
4. **One booking → one attempt** — `bookings.paymentAttemptId` is a single scalar
   column, so a booking can never hold two consumed attempts (test 6).
5. **Same booking + same user** — the two composite FKs from `bookings` to
   `payment_attempts` reject a consumed attempt that belongs to a different booking or
   a different user (tests 7a, 7b).

The transactional consumption protocol (conditional `UPDATE ... WHERE
paymentAttemptId IS NULL` under `SELECT … FOR UPDATE`) is **documented for P4-3**; the
schema already makes the unsafe outcome impossible.

## 8. Flight provider mutual exclusion and zero-selection handling

**Decision: the existing `providers` table cannot safely enforce "exactly one".**
A partial unique index only enforces *at most one*, permits *zero*, and would hard-fail
on a database that already has both providers active. P4-1 therefore adds a dedicated
**singleton selection record** and keeps the partial unique index as the hard backstop.

- `provider_selection` — `selectionKey` PK with `CHECK (selectionKey = 'flight')`, so
  the table holds **at most one** row. `providerKey` is an FK to `providers`.
- `uq_one_active_flight_provider` — partial unique index on
  `providers(vertical) WHERE vertical='flight' AND "isActive"=true AND "providerKey"
  IN ('duffel-flight','nuitee-flight')`. This is the DB-level guarantee that two real
  flight providers cannot be active simultaneously (test 8). `mock-flight` (a curated
  fallback) is deliberately outside the invariant.
- **Zero-selection detection** — the system reads
  `SELECT "providerKey" FROM provider_selection WHERE "selectionKey"='flight'`.
  Zero rows ⇒ no provider selected ⇒ the caller must return an explicit
  `provider_unavailable`; **no fallback is silently chosen** (test 9).
- **Migration reconciliation** — if the pre-existing data has two active real flight
  providers, migration 6 keeps the currently effective one (lowest `priority`, then
  key) and disables the other **before** creating the index. It never promotes a
  fallback or a mock catalogue. If zero are active, it inserts no selection row.
- Existing `providerKey` values and existing `bookings.providerId` references are
  untouched.

The admin UI and the runtime switch are **not** implemented (P4-6).

## 9. Jest open-handles fix and test evidence

`backend/src/modules/ai/ai.rerank.controller.ts` — `withTimeout` now clears its timer
when the race settles:

```ts
export function withTimeout<T>(promise: Promise<T>, ms: number): Promise<T> {
  let timer: NodeJS.Timeout | undefined;
  const timeout = new Promise<T>((_, reject) => {
    timer = setTimeout(() => reject(new Error('rerank timeout')), ms);
  });
  return Promise.race([promise, timeout]).finally(() => {
    if (timer !== undefined) clearTimeout(timer);
  });
}
```

The timeout path still rejects with the same `rerank timeout` error; only the timer
lifetime changed. `backend/test/ai.rerank.timeout.spec.ts` pins it with fake timers
(`jest.getTimerCount() === 0` after resolve, after reject, and after timeout).
`npx jest --ci --detectOpenHandles test/ai.rerank.spec.ts test/ai.rerank.timeout.spec.ts`
now reports **no open handles** (P4-0 reported 7, all from this line).

## 11. Remaining risks and blockers for P4-2

1. **`processed_webhooks` vs `webhook_events`.** The current `PaymentService` still
   uses the thin `processed_webhooks` table. `webhook_events` is the durable target;
   P4-2 must migrate the replay check to it (and decide whether to drop the old
   table). Until then there are two replay stores.
2. **Dev `synchronize` + boot seed.** The `providers` partial unique index is declared
   on the entity, so a fresh dev database running `synchronize` will create it and
   `RegistrySyncService.seedDefaults` will then fail on the second active flight
   provider (it seeds `duffel-flight`, `nuitee-flight`, `mock-flight` all active). The
   existing `onModuleInit` catch falls back to the legacy ordering, so the app still
   boots, but the seed is incomplete. This is a **P4-6** concern (the admin selection
   must own the invariant); no runtime provider code was changed in P4-1.
3. **Entity index vs migration-only.** The `Provider` entity declares the partial
   unique index, so `synchronize` and the migration both create it. If the dev
   database is not rebuilt, the index is absent there until the migration runs.
4. **`bookings.paymentAttemptId` overwrite.** The schema stores one consumed attempt
   per booking; changing it is a replacement, not a second consumption. If P4-3 needs
   to allow a failed booking to consume a new attempt, that is a transactional
   decision (documented), not a schema gap.
5. **No `recovery_jobs` table.** P4-0 listed one; P4-1 does not need it because the
   confirmation lease lives on `bookings` (`confirmingSince` / `confirmingOwner`).
   A dedicated outbox/jobs table may still be wanted for P4-4.
6. **Production deployment order.** The migration is additive and idempotent, but it
   must run before any P4-2 code writes the new tables. Deploy with
   `NODE_ENV=production` (`synchronize:false`, `migrationsRun:true`) and verify the
   migration count before traffic.
7. **Rollback caveat.** Reverting migration 6 drops the index and the selection table
   but does **not** restore provider `isActive` values changed by the reconciliation;
   re-enable the intended provider explicitly afterwards.
8. **`paymentStatus` has no CHECK.** The allowed values are documented on the entity
   (`unverified | legacy_unverified | pending | verified | failed | refunded |
   partially_refunded`); P4-2 should add a CHECK once the state machine is fixed.
