## 3. How each issue was resolved

### Issue 1 — Development synchronization regression

**Root cause:** the partial unique flight-provider index was declared on the `Provider`
entity. Development runs `synchronize`, which created the index, and
`RegistrySyncService.seedDefaults` then failed when it seeded a second active flight
provider (`duffel-flight` + `nuitee-flight`).

**Fix:** the entity no longer declares the index. The index is created **only** by
migration `1731000000006`, which is the authoritative enforcement point for production
(`synchronize: false` + `migrationsRun: true`). The entity carries a comment explaining
that declaring it would only create a dev/prod divergence and a dev boot regression.

**Result:** a fresh `synchronize` schema has no flight-provider unique index, and
`seedDefaults` seeds all 7 default providers (3 active flight providers) without a
unique violation. Production migration behaviour is unchanged and verified separately
(test 1b asserts the index exists after migration, test 8 asserts it rejects a second
active real provider).

### Issue 2 — PaymentAttempt ownership integrity

**Fix:** `payment_attempts("bookingId", "userId")` now references
`bookings(id, "userId")`:

```sql
ALTER TABLE bookings
  ADD CONSTRAINT uq_bookings_id_user UNIQUE (id, "userId");

ALTER TABLE payment_attempts
  ADD CONSTRAINT fk_payment_attempts_booking_user
  FOREIGN KEY ("bookingId", "userId") REFERENCES bookings (id, "userId");
```

Because `id` is already the primary key, `(id, "userId")` is unique; the explicit
constraint exists only to back the composite FK.

**Effect:** every attempt is provably owned by the booking's owner. Combined with the
existing CUSTOMER composite FK `(attemptId, bookingId) → payment_attempts(id,
bookingId)`, a CUSTOMER transaction can no longer reference another user's attempt: the
attempt's booking must match the transaction's booking, and the attempt's user must
match that booking's owner. The consumed-attempt constraints (partial unique index +
composite FKs on `bookings`) are untouched.

### Issue 3 — ProviderSelection integrity

**Fix:** the selection is now self-validating at the database level:

1. `CHECK ("providerKey" IN ('duffel-flight', 'nuitee-flight'))` on
   `provider_selection` — rejects `mock-flight` and any other key declaratively.
2. `CHECK ("selectionKey" = 'flight')` — singleton key (already present).
3. `FK providerKey → providers(providerKey)` (already present).
4. Trigger `p4_validate_provider_selection` (BEFORE INSERT OR UPDATE) — re-checks the
   provider is **active**, is a **flight** provider, and is one of the two real flight
   providers, with explicit error messages.
5. Trigger `p4_protect_selected_provider` (AFTER UPDATE OF `isActive` ON `providers`) —
   the currently selected provider cannot be silently deactivated; clear the selection
   first.

Zero-selection remains an explicit state (no row), and the partial unique index still
prevents two active real flight providers. Existing booking provider identities and the
future admin selection authority are preserved.

### Issue 4 — Migration 6 rollback safety

**Fix:** the reconciliation is now fully reversible. Before touching any provider,
migration 6 captures the pre-migration `isActive` of both real flight providers:

```sql
CREATE TABLE p4_provider_status_backup ("providerKey" varchar(255) PRIMARY KEY, "isActive" boolean NOT NULL);
INSERT INTO p4_provider_status_backup ("providerKey", "isActive")
SELECT "providerKey", "isActive" FROM providers
WHERE "providerKey" IN ('duffel-flight', 'nuitee-flight');
```

`down()` drops the triggers/functions/index, **restores** every captured status, then
drops the backup table and `provider_selection`. Nothing is invented or silently
discarded, and re-running the migration is deterministic (the backup is recreated from
the current state).

## 8. Remaining blockers

1. **Development schema divergence (accepted, documented).** Development
   `synchronize` does not create the flight-provider exclusion index or the ownership
   composite FK — those are migration-managed and authoritative for production. A dev
   database that needs the constraints must run the migration chain
   (`NODE_ENV` unset/`DB_SYNCHRONIZE` unset ⇒ `migrationsRun: true`).
2. **`p4_provider_status_backup` persists after migration 6.** It is required so
   `down()` can restore provider status; it is dropped by `down()`. It is not a
   configuration table and must never be edited by application code.
3. **Trigger covers `isActive` only on `providers`.** Changing a selected provider's
   `vertical` or `providerKey` while selected is not blocked (rare); the selection would
   then fail re-validation on the next write. P4-6 can extend the trigger if needed.
4. **`processed_webhooks` vs `webhook_events`** and the other P4-2 items from the P4-1
   report remain unchanged (out of scope for P4-1R).
