## 3. Original retryability / concurrency defects found in source

The audit read `payment.service.ts`, `PaymentAttemptService`, `LedgerService`,
both webhook entities, the migration, the controller, the DTOs and the existing
tests, then confirmed each finding against PostgreSQL.

| # | Defect | Evidence | Consequence |
|---|---|---|---|
| **D1** | A gateway lookup that **throws** was unhandled. | `await gateway.retrievePayment(...)` was outside any try/catch (old line 615). | The exception escaped `handleWebhook` as an HTTP 500. The event stayed `received`, so it was *accidentally* retryable, but the outcome was implicit, unrecorded and indistinguishable from a crash. |
| **D2** | `unknown_payment` was treated as final. | `markWebhookEvent(..., 'ignored', 'payment_not_found')` **plus** `recordLegacyEvent(...)`. | The event was archived, so every redelivery was rejected by the legacy check. A payment that was merely not visible yet (event ordering) could **never** settle. |
| **D3** | `unknown_attempt` was treated as final. | Same pattern (`ignored` + archive). | The spec explicitly warns this is not automatically permanent. An event arriving before its attempt row existed was permanently consumed. |
| **D4** | `gateway_amount_mismatch` conflated *incomplete* with *contradictory*. | The old check was `typeof amount === 'number' && |a-b| <= tol && currency === …`; a `NaN`/non-string amount failed the first clause and was reported as a mismatch. | A structurally unusable provider response was recorded as a **confirmed** contradiction and archived, blocking a retry that could have succeeded. |
| **D5** | **A failure of the effect transaction was permanently consumed.** | The `catch` around the effect transaction wrote `failed` + archived for *every* error. | A deadlock, connection drop, lock timeout or any transient DB failure permanently blocked the event **and** left the payment unsettled. This was the most severe defect. |
| **D6** | `ignored` was a hard duplicate in the claim. | `if (existing.status === 'processed' \|\| existing.status === 'ignored') return duplicate`. | Any `ignored` event could never be retried, so the status could only ever mean "permanently not applicable" — there was no way to express "not applicable *yet*". |
| **D7** | The legacy archive was written for non-final outcomes. | `recordLegacyEvent` was called on the `unknown_payment`, `unknown_attempt`, `gateway_amount_mismatch` and `effect_rejected` paths. | The archive — whose whole purpose is "this event was finally handled" — was polluted with retryable outcomes, converting them into permanent blocks. |
| **D8** | `processedAt` was set for unresolved outcomes. | `markWebhookEvent` always wrote `processedAt: new Date()`. | Audit data claimed an event was processed when it had only failed. |
| **D9** | No status distinguished permanent from transient failure. | The CHECK allowed only `received \| processed \| failed \| ignored`, and `claimWebhookEvent` treated both `failed` and `ignored` as terminal. | Every failure had to be modelled as permanent; retryability could not be expressed at all. |

**Concurrency findings (audited, no defect).** The claim uses an explicit
`INSERT` (not `save()`, which would upsert and reset a processed row); the
effect transaction uses a compare-and-set attempt update, `INSERT … ON CONFLICT
DO NOTHING` for the ledger, `orIgnore` for the archive, and a single transaction
for attempt + ledger + event + archive. Exactly-once therefore holds
*emergently* — see §8 for the proof. No database transaction is open during any
gateway call.

## 4. Corrected event state / outcome handling

Migration 10 adds exactly one value. The outcome taxonomy is now explicit:

| Status | Meaning | Archived? | `processedAt` | Redelivery |
|---|---|---|---|---|
| `received` | claimed, no effect attempted yet (in flight) | no | null | retried |
| `retryable` | **transient** — not resolved, not archived | **no** | null | **retried** |
| `processed` | the payment transition and ledger effect committed | yes | set | hard duplicate |
| `failed` | **permanent** rejection — a *confirmed* contradiction | yes | set | hard duplicate |
| `ignored` | retained for pre-P4-2R2 rows; no longer written | — | — | hard duplicate |

`claimWebhookEvent` now consults `WEBHOOK_EVENT_FINAL_STATUSES`; `received` and
`retryable` both resolve to `retry`.

### Handler decision table (actual code)

| Situation | Status | Outcome | Archived | Reason returned |
|---|---|---|---|---|
| signature invalid | *(no row written)* | — | no | `invalid_signature` |
| no gateway for market | *(no row written)* | — | no | `unknown_gateway` |
| legacy id already archived | — | — | — | `duplicate_event_legacy` |
| event already `processed`/`failed`/`ignored` | — | — | — | `duplicate_event` |
| `retrievePayment` throws | `retryable` | `gateway_unavailable` | **no** | `gateway_unavailable` |
| `retrievePayment` returns null | `retryable` | `payment_not_found` | **no** | `unknown_payment` |
| no attempt for the gateway ref | `retryable` | `attempt_not_found` | **no** | `unknown_attempt` |
| settle-hook re-read throws | `retryable` | `gateway_unavailable` | **no** | `gateway_unavailable` |
| amount/currency **malformed** (NaN, non-string) | `retryable` | `gateway_response_incomplete` | **no** | `gateway_response_incomplete` |
| amount/currency **well-formed but contradicting** | `failed` | `gateway_amount_mismatch` | **yes** | `gateway_amount_mismatch` |
| effect transaction throws `InvalidPaymentAttemptTransitionError` | `failed` | `attempt_state_conflict` | **yes** | `attempt_state_conflict` |
| effect transaction throws anything else | `retryable` | `effect_failed` | **no** | `effect_retryable` |
| all checks pass, transaction commits | `processed` | the attempt's new state | **yes** | `PROCESSED` |

The invalid-signature and unknown-gateway paths deliberately write **nothing**:
an unauthenticated caller has no trustworthy event identity, and persisting
forged ids would let anyone grow the table. The event is rejected every time
instead.

## 5. How temporary failures remain retryable

* The event row is **never** archived on a transient path, so the legacy check
  does not block it.
* The status is `retryable`, which `claimWebhookEvent` maps to `retry`, so the
  next delivery re-enters the pipeline.
* `outcome` records *why* it has not settled (`gateway_unavailable`,
  `payment_not_found`, `attempt_not_found`, `gateway_response_incomplete`,
  `effect_failed`) for operator diagnosis, without resolving the event.
* `processedAt` stays null — the event has not been processed.
* No new attempt is created and no charge is made as a recovery shortcut; the
  retry only ever re-applies the *same* authoritative provider state.

A redelivery therefore converges: R2 proves the `unknown_attempt` case, R3 the
gateway-timeout case, R4 the transaction-failure case.

## 6. How permanent rejections are distinguished from successful processing

| | Successful | Permanent rejection |
|---|---|---|
| Attempt state | `succeeded` (or another applied target) | unchanged |
| CUSTOMER ledger row | exactly one `capture`/`succeeded` | **none** |
| Event status | `processed` | `failed` |
| `outcome` | the applied state, e.g. `succeeded` | `gateway_amount_mismatch` or `attempt_state_conflict` |
| Archived | yes | yes |

Two things are never true on a rejection: a capture row, or an archived event
that was not finally resolved. `attempt_state_conflict` is reserved for a
*confirmed* contradiction between the durable attempt state and the event's
authoritative outcome (e.g. a late `payment.failed` for a `succeeded` payment),
where retrying could only attempt an illegal downgrade.

## 7. Atomicity of transitions, ledger, event completion and archive

The effect path is unchanged from P4-2R (it was already correct) and is now
proven rather than assumed:

```
claim/INSERT webhook_events(status='received')   ── autocommit
gateway.retrievePayment(...)                     ── no transaction open
short transaction:
    transitionWithin(attempt)                    ── compare-and-set UPDATE … WHERE status = <from>
    ledger.appendWithin(...)                     ── INSERT … ON CONFLICT DO NOTHING
    UPDATE webhook_events → processed
    INSERT processed_webhooks (orIgnore)         ── the archive
```

* A rollback of that transaction removes **all four** effects together — R4
  proves the archive row is absent, the attempt is unmoved and the ledger is
  empty after a real injected failure inside the transaction.
* The ledger can never be inserted while the attempt is not committed, because
  both are in the same transaction (guarantee 3).
* The event cannot be marked `processed` before the effect commits (guarantee 4)
  — the status update is the last statement of the same transaction.
* No transaction or row lock is held across a gateway call (guarantee 9).

## 8. Concurrent duplicate deliveries

Exactly-once is achieved by four independent mechanisms, so it does not depend
on timing:

1. **The claim.** An explicit `INSERT` keyed by `(provider, eventId)`; the
   database picks the winner of a race. The loser reads the winner's row.
2. **The attempt transition.** `UPDATE … WHERE id = ? AND status = <from>`. A
   losing racer matches zero rows (`conflict`) and never overwrites.
3. **The ledger.** `INSERT … ON CONFLICT DO NOTHING` on the globally unique
   `idempotencyKey` (`capture:{attemptId}`), so a second capture for the same
   attempt is absorbed even if two transactions overlap.
4. **The archive.** `orIgnore`, so it cannot abort a concurrent transaction.

Test W2/W9 drive three concurrent deliveries: exactly one row in each replay
store, one ledger effect, one `succeeded` attempt. Test C12 drives **different**
event ids for the same payment: still one capture. Test C13 shows a late failure
event is refused with `attempt_state_conflict` and the `succeeded` payment and
its capture are untouched.

Guarantee 6 (different ids, same payment) is covered by C12; guarantee 8 (no
downgrade) by C13 and C14.

## 9. Migration changes and rollback behaviour

**Only one migration was added** — no existing migration was modified.

| # | Name | Effect |
|---|---|---|
| 10 | `P4WebhookRetryableStatus1731000000010` | Drops `chk_webhook_events_status`, re-adds it as `('received','retryable','processed','failed','ignored')`. |

* **Forward:** a pure widening. Existing rows are untouched; nothing that was
  legal becomes illegal.
* **Backward:** `UPDATE webhook_events SET status='received' WHERE status='retryable'`
  first, then restores the original four-value CHECK. No information is lost —
  a `retryable` event is exactly a `received` event with a recorded reason, and
  the reason survives in `outcome`.
* **Databases that already applied P4-2R:** migration 10 is new, so it runs
  normally. No repair-by-editing is assumed anywhere.
* **Rollback limitation:** reverting to the four-value CHECK converts every
  `retryable` event into `received`. They stay retryable by behaviour, but the
  explicit distinction is lost until migration 10 is re-applied. M8 asserts both
  directions.

## 13. Remaining limitations and risks

1. **A retryable event with a permanently bad cause is retried on every
   redelivery.** If the payment never appears, each redelivery re-runs the
   pipeline and re-fails. There is no retry worker or scheduler (out of scope),
   so this only happens when the provider actually redelivers. An operator can
   read `webhook_events.outcome` to see why it has not settled.
2. **No automatic retry.** P4-2R2 makes failures *retryable*; it does not
   retry them. A future recovery worker would consume `status = 'retryable'`.
3. **`requires_action → succeeded` is not in the attempt state machine.** A
   webhook that reports success for an attempt still sitting at
   `requires_action` (i.e. the customer paid on a provider redirect page without
   our `confirm` call) is refused as `attempt_state_conflict`. The application's
   own funnel always calls confirm first, so the shipped flow is unaffected, and
   changing the state machine is explicitly out of scope for this phase. This is
   the single most likely follow-up.
4. **`target = 'unknown'` is marked `processed`.** If the provider returns a
   status outside the known contract, the attempt is moved to `unknown`
   (reconciliation required) and the event is settled. The attempt state machine
   still permits `unknown → succeeded`, so an operator or a future reconciliation
   path can resolve it; a redelivery will not re-apply the event.
5. **Legacy identity is id-only.** A post-P4-2 event whose id collides with a
   legacy id is rejected as a legacy duplicate. The original table's semantics,
   preserved on purpose (P4-2R).
6. **Databases that ran the original P4-2 migration 8 still lack their
   historical webhook ids** (documented in the P4-2R report). P4-2R2 does not
   change that; migration 9's empty archive remains the limit.
7. **`cancelled` remains unreachable** with the mock gateway, and
   `payment.failed` on a `pending` intent is still a no-op (mock limitation,
   unchanged).
8. **The 3DS settle hook mutates gateway state before the effect transaction.**
   If the transaction fails, the mock gateway believes the payment succeeded
   while our database still says `pending`. A redelivery then reads
   `SUCCEEDED` and settles correctly, so this self-heals; a real PSP settles
   server-to-server and is unaffected.
